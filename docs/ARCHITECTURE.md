# HireFlow — ארכיטקטורה ותכנון טכני

עדכון אחרון: 2026-10-30. סטטוס: שלב 0 ותת־משימה 1.1 הושלמו. קיים שלד pnpm workspace ללא תלויות; אין עדיין קוד יישום, סכמת Prisma או תשתיות פעילות.

דרישות ותכולה: [PRODUCT.md](PRODUCT.md). מצב בפועל והמשך: [PROGRESS.md](PROGRESS.md). שמות תיקיות, ישויות ונתיבים במסמך זה הם תכנון, אלא אם נאמר אחרת.

## 1. תמונת המערכת

המלצה: Monorepo קטן עם לקוח React ושרת Express שהוא Modular Monolith — תהליך שרת אחד עם מודולים עסקיים נפרדים. אין כרגע צורך במיקרו־שירותים או בשירות AI עצמאי. כך ניתן ללמוד ולבדוק כל חלק בלי להוסיף מורכבות תפעולית מוקדמת.

```text
דפדפן: React + MUI
        │ HTTPS / JSON, Session cookie
        ▼
שרת: Express + TypeScript
  אימות זהות → הרשאות וולידציה → שירותי פיצ'רים
        ├── מאגרי נתונים → Prisma → PostgreSQL
        ├── אחסון קבצים פרטי דרך FileStorage
        ├── שכבת AI דרך AIProvider
        └── מתאמי מקורות משרות ושירותים חיצוניים

בעתיד בלבד:
Scheduler → Redis / BullMQ → Worker → אותם שירותים עסקיים
                               └── LangGraph לפי צורך בתהליכי סוכן
```

בפיתוח מוקדם, מתאמים מחזירים fixtures סינתטיים וספק AI מזויף. חיבור אמיתי אינו תנאי לפיתוח לוגיקה. בהשקה מומלץ להגיש לקוח ו־API מאותו origin כדי לפשט Sessions והגנות דפדפן; בחירת ספק פריסה תיעשה לפני שלב הפריסה.

אין ליצור את כל התיקיות הריקות מראש. מוסיפים כל feature כשמתחילים אותו. בתוך feature בלקוח: `components`, `hooks`, `api` וטיפוסים לפי צורך. בתוך feature בשרת: `routes`, `schemas`, `service`, `repository` ובדיקות לפי צורך, ללא שכבות ריקות או קובץ גדול שמרכז כמה אחריויות.

הלקוח משתף רק חוזי API, לא מודלי Prisma או מודולים של השרת. שכבת `shared` לא תהפוך למאגר לוגיקה עסקית. לא נדרשים כרגע package נפרד לכל feature או ספריית עיצוב עצמאית.

### 3.1 השלד הקיים בפועל — תת־משימה 1.1

Monorepo הוא מאגר Git משותף לכמה אפליקציות וחבילות. ה־workspace הוא האופן שבו pnpm מזהה את החבילות בתוך המאגר ומנהל אותן. בחרנו בו כדי לאפשר בעתיד שינוי מתואם בלקוח, בשרת ובחוזי ה־API, בלי תשתית ניהול מאגרים נוספת.

נוצרו רק ארבעה קובצי בסיס בשורש: `package.json`, `pnpm-workspace.yaml`, `pnpm-lock.yaml` ו־`.nvmrc`. הדפוסים `apps/*` ו־`packages/*` הוגדרו, אך התיקיות עצמן עדיין אינן קיימות. pnpm מזהה כעת רק את חבילת השורש `hireflow`.

`private: true` מונע פרסום של חבילת השורש לרישום חבילות; הוא אינו הגדרת פרטיות למאגר Git. `packageManager` בוחר pnpm מדויק; `engines` מגדיר את גרסאות הכלים שהפרויקט תומך בהן. `engineStrict: true` ב־YAML הופך חריגה מדרישות הגרסה לשגיאת התקנה. `.nvmrc` מסייע למשתמשי nvm לבחור Node, ואינו מחליף לבדו את הגרסה שרצה במחשב.

אין dependencies, devDependencies או scripts בשורש בשלב זה. תצורת TypeScript משותפת נדחתה לקוד ה־TypeScript הראשון ב־1.2, כדי לבחור הגדרות שמתאימות לקוד ממשי ולאמת אותן עם המהדר. הגדרות module, JSX ו־lib יישארו לפי סביבת היעד — דפדפן או שרת. לא נוספו פקודות בדיקה/בנייה ריקות שמדווחות הצלחה ללא קוד.

כיוון התלות בתוך השרת: route → ולידציה ו־request context → service → repository או ממשק ספק. ה־service מנהל כללים, בעלות וטרנזקציות; route מטפל ב־HTTP. מודול אחר ניגש דרך שירות/ממשק מפורש, ואינו משנה טבלאות שבבעלותו ישירות. פעולות שמחייבות עקביות בכמה ישויות מתבצעות בטרנזקציה מתואמת אחת.

כלי הסוכן קוראים לאותם שירותים עסקיים שמשמשים את ה־API. זהות המשתמש מוזרקת מה־Session או מהקשר משימת רקע מאומת, ולא מטקסט השיחה או מפרמטר שהמודל בחר.

## 5. מודל נתונים ראשוני

זהו מודל לוגי, לא סכמת Prisma סופית. ישויות נוצרות במיגרציות רק בשלב הרלוונטי. ברירת המחדל: מזהה UUID, זמנים ב־UTC, `createdAt` ו־`updatedAt` לרשומות ניתנות לעריכה; רשומות היסטוריה נשמרות ללא דריסה. שם ותצוגה אינם מפתחות זהות.

### 5.1 זהות, פרופיל וחיפוש — פרטיים למשתמש

| ישות | שדות מרכזיים | קשרים ואילוצים |
| --- | --- | --- |
| User | id, emailNormalized, displayName, locale, theme, accountState | emailNormalized ייחודי; משתמש אחד הוא גבול הבעלות, לא ארגון |
| Credential / Session | userId, passwordHash אם אימות מקומי; sessionTokenHash, expiresAt, revokedAt | User אחד לרבים; אין החזרת hash ללקוח, טוקן גולמי אינו נרשם בלוג |
| ProfessionalProfile | userId, headline, summary, generalLocation, revision | אחד לכל משתמש; revision עולה לאחר שינוי מאושר |
| Experience | userId, profileId, title, employer, startDate, endDate, isCurrent, description | פרופיל אחד לרבים; תאריכים חלקיים נתמכים בלי המצאת יום |
| Education | userId, profileId, institution, qualification, field, dates | פרופיל אחד לרבים; תואר אינו חובה לכל מקצוע |
| ProfileSkill | userId, profileId, label, normalizedKey, level?, evidenceRef? | ייחודי לפרופיל ול־normalizedKey; מילון שמות נרדפים ניתן להרחבה |
| ProfileLanguage / Certification / Project | userId, profileId ונתוני הסוג: שפה/רמה, הסמכה/תוקף, פרויקט/תיאור/קישור | אוספים נפרדים; פרויקטים אופציונליים |
| SearchProfile | userId, name, roles, sectors, seniority, employmentTypes, workModes, locations, salaryRange?, isActive, revision | User אחד לרבים; שכר כולל מטבע ותקופה, ערך חסר נשאר חסר |
| UserPreference | userId, notificationPreferences; commuteOrigin? | אחד למשתמש; הגדרות נסיעה מפורטות יתווספו בהמשך |

לרשומות שחולצו או אושרו מ־AI: מקור מסוג `manual`, `document` או `import`, הפניה למקור ומועד אישור. הצעות לא מאושרות נשמרות בנפרד. שנות ניסיון אינן מוכפלות אוטומטית במקרה של תקופות חופפות.

### 5.2 קבצים וקורות חיים — פרטיים למשתמש

| ישות | שדות מרכזיים | קשרים ואילוצים |
| --- | --- | --- |
| FileAsset | userId, storageKey, originalName, mimeType, byteSize, checksum, processingState, retentionState | מזהה אחסון פנימי, ללא URL ציבורי קבוע; קובץ מקור אינו נדרס |
| Resume | userId, title, originalFileId?, currentVersionId? | User אחד לרבים; מצביע currentVersion חייב להשתייך לאותו Resume ולמשתמש |
| ResumeVersion | userId, resumeId, versionNumber, parentVersionId?, structuredContent, targetJobId?, approvedAt?, profileRevision? | Resume אחד לרבים; ייחודיות resumeId + versionNumber; גרסה קודמת אינה נערכת במקום |
| ResumeAnalysis | userId, resumeVersionId?, sourceFileId?, extractedProposal, findings, providerMeta, analysisVersion, state | מתעד טיוטת חילוץ/ניתוח ומקורות; אינו פרופיל מאושר |
| ResumeChangeProposal | userId, baseVersionId, proposedChanges, factualChanges, state, reviewedAt? | אישור מייצר גרסה חדשה; דחייה משאירה מקור; הצעה מיושנת דורשת סקירה מחדש |

מידע מובנה ב־JSON מתאים לתוכן קורות חיים, ממצאי ניתוח ופירוט ראיות, עם schema version וולידציה. בעלות, קשרים, סטטוסים ושדות חיפוש עיקריים נשמרים בעמודות וקשרים יחסיים. ספריית פענוח DOCX/PDF ויצירת DOCX תיבחר לפני המימוש, לאחר בדיקת עברית ו־RTL.

### 5.3 קטלוג משרות — מידע משותף ולא אישי

| ישות | שדות מרכזיים | קשרים ואילוצים |
| --- | --- | --- |
| Company | name, website?, industry?, activitySummary?, evidenceUrl?, verifiedAt? | חברה אחת לרבות JobPosting; אין מיזוג לפי שם בלבד |
| JobPosting | companyId, title, description, locations, workMode?, employmentType?, salary?, requirements, status, revision | המשרה הקנונית; שדות חסרים נשארים nullable; דרישות מציינות חובה/רצוי/לא ידוע ומקור |
| JobSourceRecord | jobId, sourceType, sourceTenantKey, externalId, canonicalUrl, publishedAt?, fetchedAt, lastVerifiedAt?, sourceStatus, contentHash | ייחודיות sourceType + sourceTenantKey + externalId; כולל מזהה לוח/חברה כשהמזהה אינו גלובלי |

JobPosting אחד עשוי להיות מקושר לכמה רשומות מקור. קליטה חוזרת מעדכנת מקור קיים באופן idempotent. זיהוי כפילויות בין מקורות הוא שמרני, לפי URL/מזהים וראיות נוספות; לא ממזגים רק כי כותרת וחברה דומות. משרה יכולה להיות `active`, `expired` או `unknown`; היעדר מידע אינו `expired`.

### 5.4 התאמה ומועמדויות — פרטיים למשתמש

| ישות | שדות מרכזיים | קשרים ואילוצים |
| --- | --- | --- |
| MatchResult | userId, jobId, searchProfileId, profileRevision, searchRevision, jobRevision, methodVersion, score?, coverage, breakdown, evidence | היסטוריית תוצאות; cache תקף רק לאותו משתמש ולגרסאות הקלט; score חסר כשאין בסיס מספק |
| SavedJob | userId, jobId, savedAt | ייחודיות userId + jobId |
| Application | userId, jobId, resumeVersionId?, status, companySnapshot, jobSnapshot, contact?, preparedAt?, submittedAt?, acknowledgedAt?, lastUpdatedAt | ייחודיות userId + jobId ב־MVP; קורות החיים חייבים להיות של אותו משתמש |
| ApplicationStatusEvent | userId, applicationId, fromStatus?, toStatus, source, occurredAt, evidenceRef?, note? | אחד לרבים, היסטוריה ללא דריסה; source הוא user או integration, לא ניחוש AI |

תצלום פרטי החברה והמשרה במועמדות שומר את ההקשר גם אם הקטלוג משתנה. אין צורך בישות מעסיק פרטית נוספת. איש קשר נשמר רק אם ידוע, עם מינימום מידע. ניסיון הגשה חוזר לאותה משרה יהיה בעתיד אירוע נוסף או מחזור מתועד; אין להסיר את האילוץ ללא החלטה מפורשת.

### 5.5 שיחה, אישורים והרחבות

| ישות | שדות מרכזיים | קשרים ואילוצים |
| --- | --- | --- |
| Conversation / Message | userId, conversationId, role, content, createdAt, toolReferences? | User אחד לרבות שיחות, שיחה אחת לרבות הודעות; היסטוריה רגישה עם מדיניות שמירה |
| ActionApproval | userId, conversationId?, actionType, payloadHash, targetRevision, expiresAt, state, decidedAt?, consumedAt? | אישור להצעה מוגדרת וגרסה מוגדרת בלבד; אינו אישור כללי לכלים |
| AuditEvent | userId?, actorType, action, entityType, entityId, requestId, outcome, occurredAt | ללא תוכן קורות חיים/שיחות/סודות בלוג; שימור מזהה משתמש לאחר מחיקה ייקבע במדיניות |
| CommuteEstimate — עתידי | userId, jobId, originRef, destinationRef, mode, departureTime, duration, distance, cost?, provider, calculatedAt | מפתח cache לפי מסלול/זמן/ספק ומדיניות פרטיות; לא מייצרים בלי יעד תקף |
| SearchSchedule / Notification — עתידי | userId, searchProfileId, timezone, schedule, enabled; channel, deliveryState | עיבוד חוזר בטוח, העדפות והתנגדות להתראות נאכפות בשרת |
| ExternalConnection — עתידי | userId, provider, scopes, encryptedTokenRef, expiresAt?, revokedAt? | מינימום scopes; ביטול ומחיקה; אין טוקנים בדפדפן או בהודעות AI |

קשרי הליבה: User → Profile → פריטי ניסיון/השכלה/כישורים; User → SearchProfile; User → Resume → ResumeVersion; Company → JobPosting ← JobSourceRecord; User + JobPosting → SavedJob / MatchResult / Application → StatusEvents; User → Conversation → Message. כל קשר לנתון אישי נבדק מול אותו userId, גם אם מזהה הרשומה תקין.

## 6. אילוצי נתונים והרשאות

- כל repository של נתון אישי מקבל `userId` מאומת ומבצע קריאה/עדכון/מחיקה באמצעותו, ולא רק לפי `id`.
- בצד המסד יהיו FK ואילוצי ייחודיות; קשרים בין ישויות פרטיות ייאכפו באמצעות מפתחות מורכבים כמו `(id, userId)` כשהם מתאימים, נוסף על בדיקת שירות. כך לא ניתן לשייך גרסת קורות חיים של משתמש אחר למועמדות.
- נתוני קטלוג משותפים אינם מאפשרים להסיק מי שמר או הגיש מועמדות. קבצים ומידע פרטי אינם נשמרים בטבלאות הקטלוג.
- אין `userId`, תפקיד משתמש או כתובת אחסון הניתנים לקביעה חופשית בבקשת לקוח. המספרים וה־enums עוברים ולידציה בזמן ריצה; טיפוסי TypeScript לבדם אינם הגנה.
- בדיקות בידוד עם שני משתמשים יכסו רשימות, פריט יחיד, עדכון, מחיקה, הורדת קובץ, שיחה, אישורים וייצוא. UUID אינו מנגנון הרשאה.
- RLS במסד הוא אפשרות להגנה נוספת בעתיד, לא תחליף למדיניות שירות; לא מוסיפים אותו לפני הגדרה ובדיקה של הקשר החיבור ל־Prisma.

## 7. זרימות ליבה וסטטוסים

### קורות חיים

העלאה → בדיקת קובץ → חילוץ → טיוטת עובדות עם מקור → סקירת משתמש → אישור → פרופיל/גרסת קורות חיים מאושרת. יעד השמירה מוצג למשתמש; אישור לקורות החיים אינו אישור לשינוי הפרופיל ולהפך. ניתוח ושיפור יוצרים הצעה נפרדת; אישור ההבדלים יוצר ResumeVersion חדשה עם הפניה לגרסת הבסיס. שינוי בגרסת הבסיס בזמן הסקירה מחייב סקירה מחדש. ייצוא משתמש בגרסה המאושרת שנבחרה ולא בתגובה חופשית של מודל.

### חיפוש והתאמה

מתאם מקור → נרמול וולידציה → upsert לרשומת מקור → שיוך/יצירת משרה → חיפוש לפי העדפות → מנוע התאמה. חיפוש MVP נשען על שאילתות PostgreSQL ואינדקסים מתאימים; מנוע חיפוש ו־vector DB אינם נדרשים כעת.

המנוע הראשוני הוא כללים ניתנים להסבר, עם רכיבים נפרדים לראיות, העדפות ודרישות חובה. מידע חסר נרשם כ־unknown; הכיסוי מוצג בנפרד מהציון, ומשקלים/סף מינימום לציון ייקבעו בשלב 7.1. AI יכול לסייע בחילוץ או בניסוח הסבר אך אינו מייצר הסתברות קבלה. תוצאות נבחנות בדוגמאות ממספר תחומי עיסוק, כולל מקצוע הדורש הסמכה פורמלית.

### מועמדות

`prepared` → `submitted` → `acknowledged` → `interviewing` → `offer` / `rejected` / `withdrawn` / `closed`.

זהו אוצר סטטוסים ולא חובה לעבור בכל שלב: אירועים אמיתיים יכולים לדלג על שלבים, ותיקון ידני נשמר כאירוע חדש עם סיבה. `prepared` דורש הכנה בלבד; `submitted` נובע מדיווח משתמש או תוצאת אינטגרציה מורשית; `acknowledged` מחייב עדות מפורשת לקבלה ממערכת הגיוס או דיווח משתמש המציין עדות כזו. בכל מקרה מוצגים מקור המידע והאם אומת באינטגרציה. פתיחת קישור אינה משנה סטטוס הגשה. SavedJob אינו Application.

### פעולת סוכן ושינוי מידע

בקשת משתמש → קריאת נתונים מורשים → הצעה מדויקת → תצוגת השינוי לאישור → אימות המשתמש, התוקף וגרסת היעד → ביצוע בשירות העסקי → Audit ותוצאה.

האישור קשור ל־payloadHash ולגרסת יעד; שינוי הצעה, גרסה או יעד מבטל את תקפותו. אישור וביצוע פנימי נצרכים אטומית כדי למנוע ביצוע כפול. הצעה לשינוי קורות חיים נשארת בבעלות resumes; ActionApproval מקשר אליה ואינו יוצר מקור אמת מתחרה.

בעתיד, הגשה חיצונית תצריך גם idempotency key, תיעוד ניסיון ומענה למצבי timeout/תוצאה לא ידועה. אין לבצע retry עיוור אחרי תשובה לא ברורה מספק חיצוני. Worker לא יוכל להרחיב הרשאה או למחזר אישור להצעה אחרת.

## 8. API, טיפוסים ושגיאות

- API בסגנון REST תחת `/api/v1`; לדוגמה משאבי `profile`, `search-profiles`, `resumes`, `jobs`, `matches`, `applications` ו־`conversations`. אלו שמות תכנון, לא endpoints קיימים.
- ה־web משתמש ב־API client משותף, ללא גישה ישירה למסד או ל־SDK של ספק AI.
- `packages/contracts` מכיל DTO וסכמות בדיקה בזמן ריצה; ספריית הסכמות תיבחר בעת הקמת החוזה הראשון. DTO נפרד ממודל מסד כדי שלא לדלוף hashes ושדות פנימיים.
- שגיאה מחזירה קוד יציב, שדות קלט רלוונטיים ו־requestId; הלקוח מתרגם הודעות. אין להחזיר stack trace או תשובות ספק המכילות מידע רגיש.
- רשימות עם pagination, סינון ומיון מפורשים. כתיבות עם revision למניעת דריסה; אילוצי מסד וטרנזקציות מונעים כפילויות גם בבקשות מקבילות.
- UI שומר מצב עריכה ו־Loading/Empty/Error/Success מקומית לפי feature; ניהול state גלובלי נוסף רק אם מתעורר צורך.

## 9. ספקים חיצוניים ו־AI

ממשקים מתוכננים: `AIProvider`, `JobSourceAdapter`, `FileStorage`, `ResumeParser`, ובהמשך `RoutingProvider`, `SubmissionAdapter` ו־`NotificationProvider`. הם מוגדרים לפי צורכי המוצר ולא לפי טיפוסים של SDK מסוים. כל מתאם מחזיר מקור, מועד איסוף ושדות לא ידועים באופן מפורש.

ל־AI: פלט schema-validated, timeout, הגבלת גודל קלט/פלט, מעקב שימוש ותקציב לכל משתמש. אין להעביר מסמך שלם כשמספיקים שדות נבחרים. מדיניות ספק לגבי שימוש במידע, שמירה ואזור אחסון תיבדק לפני מידע אמיתי. אין הבטחה לחוסר שמירה אצל ספק לפני בדיקת התנאים שלו.

טקסטי קורות חיים, משרות ואתרים הם קלט לא מהימן. הוראות בתוכם אינן יכולות להעניק הרשאות, לבחור userId, לפתוח כלים חדשים או לשלוח סודות. כלים מוגבלים מראש, ולכל קריאה יש ולידציה והרשאה בשרת. כתובות מקור וחילוץ קבצים מטופלים גם מול SSRF, קבצים זדוניים וצריכת משאבים עודפת.

בקשות ספק קריאות בלבד יכולות לעבור retry מוגבל עם backoff וכיבוד מגבלות ספק; כתיבות חיצוניות דורשות מנגנון מפורש. חיבור Greenhouse/Lever/LinkedIn ומפות ייבדק מול התיעוד העדכני בשלב החיבור; מסמך זה אינו קובע שהרשאות או API מסוימים זמינים כיום.

## 10. אבטחה, פרטיות ומחזור חיי מידע

- TLS בפריסה, סודות דרך תצורת שרת בלבד, ללא מפתחות ב־Vite env ציבורי. `.env.example` יכיל שמות ודוגמאות ללא סודות.
- Session cookie מוגן, הגנה על בקשות משנות מידע מפני CSRF, מדיניות CORS מצומצמת והגבלת קצב לפי פעולה ומשתמש. Session מבוטל בהתנתקות ובמחיקת חשבון.
- אחסון פרטי מוצפן בדיסק/שירות האחסון; הצפנה ברמת יישום לטוקני אינטגרציה ומידע רגיש בהתאם להערכת הצורך. ניהול מפתחות נפרד ממסד הנתונים.
- בהעלאה: בדיקת סוג בפועל, גודל, מספר עמודים/טקסט, מגבלות decompression ל־DOCX, פענוח ללא הרצת תוכן פעיל וניקוי קבצים זמניים. אמצעי סריקה ובידוד יוגדרו בשלב 5.1.
- הורדה רק לאחר בדיקת בעלות; אם משתמשים בקישור חתום הוא קצר־תוקף. שמות קבצים מנוקים, ואין אמון בנתיב שהלקוח שולח.
- לוגים כוללים מזהי בקשה/פעולה ותוצאה, ללא טקסט מסמכים, סיסמאות, Session tokens, מיקום מוצא או שיחות מלאות.
- נתונים מאושרים נשמרים כל עוד המשתמש זקוק להם; לקבצים זמניים, הצעות שנדחו, שיחות, לוגים וגיבויים יהיו TTL ותנאי שמירה מוגדרים לפני אחסון מידע אמיתי. מספרי הימים עדיין לא הוחלטו.
- מחיקת חשבון מבטלת גישה תחילה, ואז מוחקת פרופיל, חיפושים, קבצים, גרסאות, התאמות, מועמדויות, שיחות, Cache וחיבורים חיצוניים. קטלוג משרות משותף יכול להישאר ללא קשר אישי.
- מחיקה מתאמת גם ספקים, תורים, קבצי ייצוא וגיבויים לפי יכולות ומדיניות. אם נדרשת עבודה ברקע, יש מנגנון המשך וסטטוס; אין לדווח שהמחיקה הסתיימה לפני שהשלבים הנדרשים הושלמו. משימות ישנות אינן משחזרות משתמש שנמחק.
- גיבויים אינם מוצגים כנמחקים מיידית אם אין יכולת כזו. מדיניות השמירה ומנגנון שחזור שמחיל מחדש מחיקות קודמות ייקבעו לפני פריסה.
- ייצוא מידע אישי יכיל נתונים מובנים וקבצים השייכים למשתמש; Excel של מועמדויות הוא יכולת נפרדת ואינו תחליף לייצוא מלא.

## 11. עלויות, Cache ותפעול

Cache של קטלוג משותף אפשרי לפי מקור וטריות; Cache של התאמות/AI פרטי לפי userId, גרסאות קלט, שיטת חישוב וגרסת prompt. אין לשתף תגובות אישיות בין משתמשים. שינוי פרופיל או משרה מבטל תוצאה מיושנת; מחיקה מנקה את ה־Cache הרלוונטי.

מגבלות העלאה, מספר תוצאות, תדירות חיפוש ותקציב AI נאכפות בשרת ומוגדרות בתצורה. ערכים מספריים ייקבעו לאחר מדידה בשלב המתאים, ולא על בסיס הבטחת ביצועים בשלב 0. אין cache מבוזר או Redis עד שנדרש.

פעולות קליטה וייצוא חוזרות חייבות להיות בטוחות. ב־BullMQ עתידי משימות יכילו מזהים מינימליים וייבדקו מחדש מול מצב המשתמש, ההרשאות והביטול. יוגדרו ניסיונות מרביים, כשל סופי וניטור. מזהה משימה לבדו אינו מחליף idempotency במסד.

לפני פריסה: מיגרציות נבדקות על עותק נתונים, גיבוי ושחזור נבדקים, ומוגדרים לוגים מצונזרים ומדדי זמני תגובה/כשל/שימוש ספקים. אין תשתיות אלו בשלב הנוכחי.

## 12. אסטרטגיית בדיקות

- Vitest: כללים עסקיים, דרישות חובה/רצוי/חסר, סטטוסים, מניעת כפילויות, אישורים ותקפות גרסאות. בדיקות משקפות התנהגות ותרחישי כשל, לא רק את מבנה הקוד.
- אינטגרציה עם PostgreSQL מבודד: אילוצי בעלות וקשרים, טרנזקציות, בקשות מקבילות ו־Sessions. Mock של repository אינו מוכיח את אילוצי המסד.
- מתאמים: fixtures וספקים מזויפים, שדות חסרים, שגיאות, timeout ושינוי מבנה. בדיקת חיבור אמיתי נפרדת ומוגבלת, ללא סודות ב־CI.
- AI: fixtures של תוצאה צפויה, פלט לא תקין, ניסיון הזרקת הוראות, אי־המצאת עובדות, אישור ודחייה; הערכה ידנית מתועדת לתוצאות אמיתיות בכמה מקצועות.
- מסמכים וייצוא: קובצי דוגמה סינתטיים בעברית ובאנגלית, PDF ללא טקסט, DOCX פגום, הבדלים וקריאות ייצוא. Excel מונע פרשנות תוכן מיובא כנוסחאות לא רצויות.
- Playwright בהמשך: מסלול MVP, בידוד שני משתמשים, כיווניות, מקלדת, מובייל ומצבי כשל. בדיקת נגישות אוטומטית תלווה בבדיקה ידנית.
- לכל תת־משימה מריצים בדיקות רלוונטיות, typecheck ו־build כאשר קיימים; מתעדים במפורש בדיקות שלא ניתן להריץ. בשלב 0 אין עדיין סביבת בדיקות או build.
